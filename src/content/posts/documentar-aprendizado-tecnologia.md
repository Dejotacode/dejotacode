Estudar tecnologia sem registrar o que aconteceu faz você depender demais da memória. Depois de alguns dias, um comando que parecia óbvio pode virar uma sequência de tentativas até funcionar de novo.

Documentar não significa escrever textos longos. Significa deixar pistas suficientes para que você consiga repetir, explicar e melhorar o que fez.

## Registre o problema antes da solução

Em vez de guardar apenas um comando, anote o contexto.

```text
Problema: o projeto não iniciava.
Sintoma: o terminal mostrava que uma dependência não existia.
Ação: instalei as dependências do projeto.
Resultado: o servidor iniciou normalmente.
```

Essa estrutura ajuda a lembrar por que uma ação foi necessária.

## Explique comandos com uma frase

Se você salvar um comando, escreva ao lado o que ele faz naquele contexto.

```bash
npm install
```

Anotação útil: instala as dependências declaradas pelo projeto antes de iniciar o ambiente local.

Isso é melhor do que manter uma lista enorme de comandos sem explicação.

## Guarde erros que ensinaram alguma coisa

Nem todo erro merece documentação. Registre os que:

- demoraram para ser entendidos;
- podem aparecer novamente;
- revelaram um conceito importante;
- mudaram sua forma de trabalhar.

Um erro bem documentado vira referência para o futuro.

## Use um README pequeno em projetos

Um `README.md` pode começar com cinco perguntas:

1. O que este projeto faz?
2. Por que ele existe?
3. Como executar ou abrir?
4. O que já foi concluído?
5. Qual é o próximo passo?

Você não precisa esperar o projeto ficar pronto para criar esse arquivo.

## Registre decisões, não apenas resultados

Quando você escolher uma tecnologia, estrutura ou abordagem, anote a razão.

```text
Decisão: usar HTML e CSS puros no primeiro protótipo.
Motivo: validar estrutura e responsividade antes de adicionar JavaScript.
```

Esse tipo de registro mostra raciocínio e ajuda muito quando o projeto vira material de portfólio.

## Faça uma revisão semanal curta

No fim da semana, responda:

- o que aprendi de verdade?
- qual problema agora consigo resolver sozinho?
- qual comando ou conceito ainda preciso consultar?
- o que produzi que pode ser mostrado?
- qual é o próximo passo concreto?

A revisão não precisa durar muito. O valor está em transformar atividade em evidência de progresso.

## Não transforme documentação em procrastinação

O objetivo é ajudar o trabalho, não substituí-lo. Se você passa mais tempo formatando anotações do que praticando, simplifique.

Uma boa documentação é aquela que você realmente volta a usar.
